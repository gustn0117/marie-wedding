# 마리에 확장성 로드맵 (성장 대비)

작성일: 2026-07-18. 전면 확장성 감사(12축, 74건 확정→고유 ~12이슈)의 결과 중,
**정상 동작을 깨지 않고 지금 바로 적용 가능한 안전 배치는 이미 반영**했고(아래 "완료"),
나머지는 리스크/인프라 결정이 필요해 이 로드맵으로 남긴다.

현재 데이터는 테스트 수준(테이블 0~3행)이라 **지금은 전부 무영향**이다. 각 항목의
"임계"는 그 문제가 실제로 드러나기 시작하는 규모다.

## 이미 반영 완료 (fix124)

- **인덱스 4종 추가**: jobs 정렬(is_promoted,created_at)·이력서첨부 인가용 snapshot GIN·
  프로필 이름검색 trgm·대화목록 participant_b.
- **홈 count:'exact' 5회 제거**: 화면에 안 쓰이는 사문화 카운트라 목록쿼리를 인덱스
  6행에서 멈추게 함.
- **SSR 읽기 15초 타임아웃**: 공유 DB 지연 시 워커 무한점유 방지.
- **알림벨 백그라운드 탭 폴링 중단**: 접속자 비례 상시 인증부하 제거.

## Tier 1 — 성장 전 손봐야 함 (새 인프라 불필요, 리스크 낮음)

1. **목록 count:'exact' → 'estimated'** (jobs/directory/community/events/admin 목록)
   - 임계: 활성행 ~1만 이상. 그때부터 매 목록요청이 필터셋 전체를 카운트 스캔.
   - 주의: estimated 는 작은 테이블에서 부정확 → 지금 바꾸면 현재 페이지네이션이 깨진다.
     테이블이 커진 뒤(ANALYZE 통계 유의미) 전환하거나, "행수 < N 이면 exact" 하이브리드.
2. **목록 select('*') 과다조회 → 명시 컬럼**: jobs/community 목록이 카드에 안 쓰는
   description·content(리치 HTML 수십KB)까지 매 요청 동봉. 카드가 실제 쓰는 컬럼만 select.
   - 임계: 행수×본문크기. payload/대역폭/직렬화 비용 선형 증가.
3. **무한 로드 → 페이지네이션/가상화**: 쪽지 스레드(limit 없이 전체), 게시글 댓글(전체+
   매 렌더 재정렬), 대시보드 KPI(range 0,99 상한으로 조용히 축소표시), stats(limit 5000
   초과 시 침묵), 지원자 목록(커서 전체 순차 await).
4. **applications/create 인라인 SMTP await 제거**: 지원 응답이 자체 Postfix 상태에 직결
   (최대 15s). 이메일 발송을 백그라운드(fire-and-forget)로 분리해 지원 응답을 즉시 반환.
5. **storage-orphan-cleanup 스트리밍화**: 8개 테이블 전량+본문 HTML을 한 워커 힙에 적재 +
   10만행 하드캡 초과 시 영구 실패. 페이지를 받는 즉시 참조 Set 으로 접어넣고(메모리 O(page)),
   100k 캡을 커서+시간예산으로 교체, 연속 실패 시 실제 알림. **파일을 지우는 코드라 신중히
   구현·테스트 필요**(그래서 이번엔 correctness 버그만 고치고 스케일 재작성은 보류).

## Tier 2 — 인프라/제품 결정 필요

6. **공개 페이지 캐싱 부재**: 전부 no-store + force-dynamic → 익명/봇 트래픽이 매 요청
   공유 Postgres 직격(흡수층 0). 공개 목록·상세에 ISR(revalidate: N초) 또는 CDN 캐싱 도입.
   - 결정 필요: 허용 지연(예: 30~60초 staleness). 개인화 헤더는 쿠키기반 별도 컴포넌트라 무관.
7. **미들웨어 매 네비게이션 getUser+profiles 조회**: 페이지 이동마다 GoTrue 왕복 → 공유
   인증서버 부하 배수. 단기 서명 세션쿠키로 대부분 이동에서 getUser 생략, 또는 프로필 조회 캐싱.
   - 인증 민감 → 신중히.
8. **레이트리밋/남용 방어(공유 저장소 필요)**: 인메모리 한도는 4워커×blue/green 에서 실효
   4~8배 완화 + 배포 시 리셋. posts/comments/messages/applications/support/signup/otp 에
   per-user·per-IP 쿼터·캡차 없음. → Redis 또는 DB기반 레이트리밋 + 공개 쓰기/OTP 에 Turnstile.
   - 보안·비용 직결(스팸·OTP 발송비·SMTP 평판). 성장 시 우선.
9. **비공개 스토리지 프록시 스트리밍**: 이력서 사진/PDF 를 Next 앱이 직접 download→stream →
   트래픽 증가 시 앱이 파일서버로 전락(대역폭·이벤트루프). Supabase createSignedUrl(단기)로
   전환해 스토리지/CDN 이 바이트를 서빙, 앱은 인가만.
10. **관리자 브로드캐스트**: 단일 42s 요청+순차 자체SMTP 발송. 수천 수신자 완주 불가 +
    공유 SMTP IP 평판 소모(→ OTP/비번재설정/지원알림 동반 차단). 큐/워커 + 스로틀 +
    전용 IP/웜업, 또는 트랜잭션 메일 프로바이더.
11. **useAuth 디듀프 부재**: 페이지당 마운트된 소비자 수만큼 /api/profile/me(getUser+40컬럼
    SELECT) 중복 호출. 공유 컨텍스트/프로바이더 또는 SWR 디듀프.
12. **recalc_response_metrics 트리거**: application 쓰기마다 고용주 전체 지원서 재집계(O(N)).
    증분/비동기화.
13. **마이그레이션 정책**: 향후 큰 테이블 인덱스는 CREATE INDEX CONCURRENTLY(기존 80개는
    비-concurrent — 지금은 무해하나 대형 테이블에서 락).

## 요약 우선순위

성장 곡선에 맞춰: **8(레이트리밋/남용) → 6(공개캐싱) → 7(미들웨어) → 9(스토리지 signed URL)
→ 5(정리 스트리밍) → 1~4(쿼리 다이어트)** 순으로 손보길 권장. 결제 관련은 제외(미사용).
